# 项目规格说明书（Project Spec）模板

> 用法：复制到你的项目，一次性填好后**很少改动**（技术栈、目录结构变了才改）。
> 它是项目的"锚"：AI 每次新会话读它，就知道项目全貌、技术约束、文件该放哪——**防止路径漂移和擅自换栈**。
>
> 配套关系：本文件管"项目全貌与目录锚"；`functional_requirements_template.md` 管"每个功能做什么"；
> `EXECUTION_PROTOCOL.md` 管"怎么执行"；`development_guidelines.md` 管"红线"。

## 写作原则

1. **一页以内**：它是地图不是百科全书，细节放 FR 和规范文件
2. **目录树每个文件都注职责**：AI 放错文件是高频事故，注释就是它归位的依据
3. **约束写禁令不写愿望**："禁止换栈""固定端口 5555"有用，"尽量保持稳定"没用
4. **结构变了必须同步更新**：目录树与现状脱节比没有更糟——AI 会按旧图施工（真实事故）

---

## 骨架

```markdown
# Project: <项目代号>

# Project Specification (项目规格说明书)

## 1. Project Overview (项目概况)

* **Goal:** <一句话：做什么系统，解决什么问题>
* **Target User:** <谁用>
* **Core Value:** <为什么值得做，一句话>

## 2. Tech Stack & Constraints (技术栈与约束)

* **Frontend:** <框架 + 版本>（构建命令：<cmd>）
* **Backend:** <语言 + 框架>（开发默认端口: <port>，固定，不得占用其他端口）
* **Database:** <选型 + 文件位置>
* **Config Management:** <配置文件放哪、命名规则>
* **禁止事项:** 未经确认不得更换技术栈 / 不得引入新依赖（按需删减）

## 3. File Structure (目录结构规划)

/<project_root>
├── <entry_file>                 # <职责一句话>
├── docs/
│   ├── changelog/               # 变更记录（一天一份，规范见 guidelines §17）
│   └── specs/                   # 规格资产（本文件 / FR / 规范）
├── backend/
│   └── app/
│       ├── api/                 # 路由层（按职责拆分，单文件 ≤200 行）
│       └── services/            # 业务逻辑层
├── frontend/
│   └── src/
│       └── pages/               # 页面组件
├── tests/                       # 检查脚本（独立存放，与业务代码解耦）
└── snapshots/                   # 完工快照（Step 间交接的上下文基准）

## 4. Non-Goals (本期不做)

* <明确不做的功能>——防止 AI "顺手"把范围外的功能也做了
```

---

## 注解

| 小节 | 防的是什么事故 |
|------|---------------|
| 固定端口写进约束 | 端口被占导致"假运行"——程序看着在跑，实际永远不响应 |
| 目录树注职责 | AI 把新文件随手放根目录 / 放错层，后期找不到、路径全乱 |
| Non-Goals | AI 热心过头，范围蔓延，引入未经验收的代码 |
| 禁止换栈/引依赖 | AI 遇到问题时"换个库试试"，依赖膨胀、环境不可复现 |

> 真实项目经验：这份文件在项目中期因为"目录树与现状脱节"引发过一轮返工——
> **改了结构就当天更新本文件**，别等。
